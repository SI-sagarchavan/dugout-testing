# What the Widget Builder has that we haven't planned

Status: assessment, 2026-11-02. Sources: `fanxp-web-renderer` `feature/widget-builder` (`packages/widgets`, runtime 0.6.0, its docs, validator and changelog) and `wnm-fanxp-frontend` `feat/widget-builder` (`features/widget-builder`: editor, data panels, Assistant). Checked against `spec.md` and `primitives.md` in this folder and against the code here.

Each item says what they have, whether we have or planned it, and how it lands on the stack we've chosen (Radix, Swiper, our `{ }` binding, XState, TanStack Query, Next.js client components). Priority: **P1** = needed in the first primitives and runtime stage · **P2** = before dynamic sections ship · **P3** = tooling or later.

## 7 · Validator rules we don't have

From `validate.ts`, with errors that block publishing and warnings that guide:

- unknown prop on a type; `bind` on a type that is not bindable; a child type the parent doesn't accept (`childTypes`)
- an event a node emits that no transition handles; an `on` key the type doesn't emit
- a source read in the tree, in computed values or in the workflow **that nothing fetches** (error)
- an interval under 5 s; a `progress` status without an error exit
- an unresolved hook (preview only); an empty input mapping; a sample-only source at publish
- `stagger` without a repeat; a `hideOn` that hides a node at every width
- bare expressions where a path is expected (`when`, `over`)

Plus ours from `spec.md`: sticky under a clipping ancestor, autoplay without a pause control.

## 8 · Production delivery (not planned anywhere)

- The page renderer places a widget as a template: `content_type: "widget"`, `widget: { id, version, render, props, definition }`, served from the backend render API with only **published** versions; publishing changes what pages load once the cache expires. **We have not decided how a Figma-built section reaches the website.** The same path is the obvious choice: a template whose content is our tree, version-pinned, with `render: server \| client`.
- Drafts vs published versions, per section, with the page pinning a version.
- Security rules applied by the renderer, not trusted from the tree: only `https:`, `data:image/` and root-relative URLs; markdown as a safe subset with no HTML; colours as tokens only.

## 9 · Gaps they have too, to design in from the start

Their capability-gaps list. Cheap to plan now, expensive to retrofit:

- **i18n**: translatable strings and locale-aware formats (we have logical start/end, but every string is literal)
- **user or auth context**: "my rank" and "my team" need a `user` scope in binding and in Cast inputs
- **persisted state**: a half-built pick survives a reload (`persist: "session" | "local"` per state key)
- **timers under 5 s** and **"at time X"** triggers (when a countdown reaches zero, sales open): XState `after` with an absolute time
- **real-time push** (SSE or WebSocket): TanStack Query can take pushed data with `setQueryData`
- **list virtualisation and "load more"** for long feeds and ball-by-ball commentary
- **drag and drop** (fantasy, ranking)

## Decisions this raises

1. **`computed`**: (a) JSONata as they use it, kept out of node props; (b) a small closed set of list operations (`filter`, `sort`, `slice`, `groupBy`, `sum`) in our own syntax; or (c) none, with all shaping done in the Cast hook. Recommendation: (b). It keeps binding simple and closed, and covers tab filters and sorting.
2. **XState guards and `if`**: use our existing `when` predicate grammar (`{ path, eq|in|gt… }`) rather than JSONata. Recommended, for the same reason.
3. **Semantic aliases for Radix chrome**: who defines them per tenant, the theme export or a guess from token names (as they do).
4. **How a Figma section ships**: as its own template type, as a `widget` template, or both.
