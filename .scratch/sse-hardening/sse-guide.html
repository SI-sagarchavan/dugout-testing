  1. The dugout worker runs an agent. Every event it emits (a token, a tool call, a question, the run ending) gets a seq, a number that goes up by one for each event of that run. The worker writes the event twice: to the run's own stream in Valkey, and to the client's feed, a second stream that holds every run's events for that client.
  2. The backend (Fastify) keeps an HTTP response open per Studio tab and copies what appears in Valkey onto it, as Server-Sent Events.
  3. The Studio reads that response as it arrives, parses the frames, and hands each event to whoever listens: the query cache and the run view on screen.

02Ways to push from a server

HTTP was built for the browser to ask and the server to answer. "Push" means the server sends something nobody asked for at that moment. There are four common ways to do it.

TechniqueHow it worksDirectionGood for
PollingThe browser asks every N seconds: "anything new?"Client asksRare changes; simplest. Wastes requests and adds up to N seconds of delay.
Long pollingThe browser asks; the server holds the request open until something happens, answers, and the browser asks again.Client asks, server delaysOld browsers and proxies. One request per message.
Server-Sent Events (SSE)One ordinary HTTP response that never finishes. The server writes text frames into it as things happen.Server → client onlyFeeds, progress, logs, LLM tokens. Plain HTTP, so proxies, auth and load balancers all just work.
WebSocketAn HTTP request upgrades to a separate two-way protocol over the same TCP connection.Both waysChat, collaborative editing, games: when the client sends often too.

The Studio only needs to receive. It sends rarely (answers, comments, cancel), and those go as normal POST requests. That makes SSE the standard choice here: it is just HTTP, reconnecting and resuming are part of the standard, and nothing extra has to run on the servers. Most LLM APIs stream tokens the same way, the Anthropic and OpenAI APIs included.

WebTransport is a newer option built on HTTP/3. You'll see it mentioned, but it isn't needed here.

03The SSE wire format

SSE is a tiny text protocol. The response has Content-Type: text/event-stream, and the body is a series of frames (the spec calls them events).

Frames, fields and the blank line

A frame is a group of lines, ended by an empty line. Each line is field: value. Only four fields mean anything:

FieldMeaningExample from our backend
dataThe payload. Several data: lines in one frame are joined with a newline. A frame with no data is not delivered.data: {"runId":"r1","seq":7,…}
eventThe frame's name, so one stream can carry several kinds of message. Without it the name is message.event: run.updated
idThe frame's position. The client remembers the last one it saw and sends it back when it reconnects. See Resuming.id: 42 (per-run) or id: 1731052800123-0 (feed)
retryHow long a browser's EventSource waits before reconnecting, in milliseconds.retry: 2000

A line that starts with a colon is a comment. It carries nothing but still sends bytes over the wire, which is exactly what a heartbeat needs: : heartbeat.

In our code

The backend builds frames by hand: frame() writes id: <seq>\ndata: <json>\n\n, the feed writes id, event and data, and the heartbeat writes : heartbeat\n\n every 15 s. The Studio parses frames in api/sse.ts (createSseParser).

Frames don't arrive in one piece

TCP delivers bytes, not frames. One network read may hold half a frame, three frames, or a frame split in the middle of a multi-byte UTF-8 character. So a parser keeps a buffer: it adds each chunk, cuts off every complete frame (everything up to a blank line), and keeps the unfinished rest for the next chunk. TextDecoder.decode(bytes, { stream: true }) handles the split characters: it holds back an incomplete character until the next chunk completes it.

Try deleting a blank line (two frames merge), adding a second data: line (joined with a newline), or removing the final blank line (the last frame waits in the buffer).

04EventSource, and why we use fetch

EventSource: the browser's built-in client

Browsers ship an SSE client: new EventSource(url). It parses frames, fires one DOM event per frame, reconnects on its own after retry milliseconds, and sends the last id it saw as the Last-Event-ID header. It's convenient, but it has hard limits:

  • It can only send a GET.
  • It can't set headers. Cookies are the only way to authenticate.
  • Its reconnect policy is fixed: no backoff, no jitter, and it gives up for good on any non-200 response.

Streaming with fetch

The other way: call fetch() and read response.body, a ReadableStream. reader.read() resolves each time a chunk arrives. You parse the frames yourself and write your own reconnect loop. In return you choose the headers, the method and the retry policy. Microsoft's @microsoft/fetch-event-source library packages this pattern; many teams write their own, as we did.

In our code

Our routes authenticate with an Authorization: Bearer header and a client header, which EventSource can't send. So http-transport.ts opens both streams through axios with adapter: 'fetch' and responseType: 'stream'. That also reuses the client's refresh-on-401 interceptor. feed.ts and follow-run.ts read the chunks, call the parser and run the reconnect loop. This is the industry-standard choice for header-based auth.

Side effect

The backend's retry: 2000 line is read only by EventSource, so for the Studio it does nothing. It's harmless, but it can suggest the wrong thing to a reader. ticket 08

05Resuming without losing or repeating events

Connections drop: wifi changes, laptops sleep, servers are deployed. What matters is what happens next.

Event IDs and Last-Event-ID

If every frame carries an id, the client can say on reconnect "the last thing I got was 41", and the server sends 42 onwards. For this the server needs a log: a record of recent events it can read from any point. A plain broadcast like Redis Pub/Sub can't do it; a stream can (section 07).

sequenceDiagram
  participant S as Studio
  participant B as Backend
  participant V as Valkey stream
  B->>S: id: 40 · data …
  B->>S: id: 41 · data …
  Note over S,B: connection drops
  S->>B: GET /events  (Last-Event-ID: 41)
  B->>V: XRANGE (0-41 … +
  V-->>B: 42, 43
  B->>S: id: 42 · data …
  B->>S: id: 43 · data …

The cursor, and why it must only move forward

The "last id seen" is a cursor: a bookmark in the log. A cursor has to be monotonic, meaning it only ever moves forward. If a frame with an older id arrives after newer ones and the client saves it, the next reconnect starts too early and replays events it already has.

Found in review

The feed sends run.updated up to 800 ms after the event that caused it, but with that event's (older) id, and the Studio saves every id it sees. The fix: only log entries (run.event) carry an id, and the client only moves its cursor forward. ticket 02

At-least-once delivery and deduplication

Messaging systems promise one of three things:

  • At most once: it may be lost, never repeated.
  • At least once: never lost, sometimes repeated.
  • Exactly once: hard to achieve over a network.

The practical goal is at least once, with a receiver that ignores repeats. Such a receiver is called an idempotent consumer: processing a message twice has the same effect as processing it once. Together they behave like exactly once.

In our code

Every event has a per-run seq. followRunLive's deliver() drops any event with seq <= after, and the backend's followRunEvents does the same in send(). That's textbook deduplication by sequence number.

Gaps: when the log no longer reaches back far enough

A log can't grow without limit, so it is trimmed: old entries are deleted. If a client resumes from an id that has already been trimmed, the server can only send what is left. The events in between are a gap, and nothing reports an error. A robust client detects or assumes a gap after a reconnect and reloads from a source that is complete.

Found in review

The client feed is trimmed to about 20,000 entries, and every token is an entry. After a long drop, the followed run can miss events, run.completed among them. The per-run stream has no gaps, so followRunLive should read it again after each reconnect. ticket 03

06Keeping a long connection alive

An SSE response may stay open for hours, and everything between browser and server was built for requests that finish in seconds.

Idle timeouts

Load balancers and proxies close a connection that has sent nothing for a while, to free resources. AWS's Application Load Balancer defaults to 60 s, and nginx's proxy_read_timeout is also 60 s. A run that thinks for two minutes without emitting anything would be cut off.

Heartbeats

The fix is to send something small at regular intervals, well inside the shortest timeout. In SSE that's a comment line, which every client ignores.

In our code

HEARTBEAT_MS = 15_000 in config.ts; the controllers write : heartbeat on a setInterval.

Half-open connections and the stall watchdog

Sometimes a connection dies without either side being told: a laptop sleeps, a NAT router drops its table entry, a cable is pulled. TCP has no traffic to notice it with, so the browser waits on reader.read() for ever. This is a half-open connection. The client-side answer is a watchdog: a timer that says "if nothing at all, not even a heartbeat, arrived for N seconds, the connection is dead; drop it and reconnect". N must be comfortably more than the heartbeat interval.

In our code

DEFAULT_STALL_MS = 45_000 in feed.ts and follow-run.ts: three missed heartbeats. A setInterval checks lastActivity and calls reader.cancel(). Good practice.

Proxy buffering and compression

A proxy may buffer a response: collect it and pass it on in large blocks, or only when it ends. For SSE that means events arrive minutes late or not at all. Compression does the same, since gzip waits for enough bytes to compress. Three headers prevent it:

  • Cache-Control: no-cache, no-transform: don't cache it, and don't rewrite it (no-transform rules out compression by intermediaries).
  • X-Accel-Buffering: no: nginx's switch for "don't buffer this response".
  • Content-Type: text/event-stream: many proxies and CDNs recognise it and stream it through.
In our code

SSE_HEADERS in the controller sets all three. Taking the response over with reply.hijack() also keeps Fastify's own compression out of the way.

The six-connection limit, and HTTP/2

On HTTP/1.1, each open SSE response takes up one TCP connection, and browsers allow about six connections per host, shared by every tab. Six tabs with one stream each and the seventh tab's API calls queue behind them. HTTP/2 multiplexes: many requests share one TCP connection as separate streams (typically up to 100), so the limit mostly goes away.

In our code

This is why the Studio keeps one feed connection (GET /surface/stream) for everything, with named events, instead of a stream per screen. Whether a second per-run stream is cheap depends on the load balancer speaking HTTP/2 to browsers. ticket 12

07The log behind the stream: Valkey Streams

Valkey is an open-source fork of Redis and speaks the same commands. A stream is one of its data types: an append-only log of entries, each with an id and a few fields.

Entry ids: <ms>-<n>

An id is two numbers: 1731052800123-0 means "the first entry added in millisecond 1731052800123". Ids only grow. You can let Valkey choose (*) or give one yourself, as long as it's larger than the last.

In our code

The run stream gives its own ids, 0-<seq>, so the Valkey id and the event's seq are the same number, and "after seq 41" becomes "after 0-41" with no lookup. The feed lets Valkey choose (*), because it mixes many runs. That's why the feed's SSE ids look like 1731052800123-0 and the per-run ones are plain numbers. Comparing two feed ids means comparing both parts as numbers; the strings won't do (ticket 02).

Why a blocking read needs its own connection

A Redis or Valkey connection handles one command at a time. While XREAD BLOCK waits, that connection can't do anything else, so every waiting reader needs a connection of its own. ioredis's duplicate() opens one with the same settings.

Found in review

Each open SSE response opens its own duplicate connection, so connections grow with the number of tabs. The usual pattern is one reader per process that shares what it reads in memory with every local response: fan-out. ticket 11

Streams vs Pub/Sub

Valkey also has Pub/Sub (PUBLISH/SUBSCRIBE): a message goes to whoever is listening at that moment and is then gone. It's simpler and faster, but there's no history, so no resume. Streams keep the history. That's why Last-Event-ID can work at all.

08The Node and Fastify side

reply.hijack()

Fastify normally owns the response: you return a value, and Fastify serialises it, runs its hooks and ends the response. For a stream that never ends, the handler tells Fastify "I'll handle the raw Node response myself" (reply.hijack()) and then writes to reply.raw directly. After that, Fastify's onSend hooks don't run, which is why our startSse copies the CORS headers by hand first.

Backpressure: write(), drain and writableLength

A socket can send only so fast; the client's network sets the pace. When you write() faster than that, Node keeps the extra in memory. write() returns false once that buffer is past a threshold (the high-water mark, about 16 KB), meaning "slow down"; the 'drain' event later says "the buffer emptied, go on". writableLength is how many bytes are waiting right now. Respecting this signal is called handling backpressure.

If you ignore it, nothing fails. The buffer just grows: a slow client on a busy stream makes the server hold megabytes, then hundreds of megabytes.

Option 1: wait

Stop reading the source until 'drain'. Right for file copies, where the source can wait.

Option 2: drop the slow client

Past a limit, close the connection. The client reconnects with Last-Event-ID and the log replays what it missed. Right for live feeds backed by a log, as ours is.

Found in review

Our controllers ignore write()'s return value. The plan: cap the buffer at 1 MB, then destroy the connection. ticket 05

09Behaviour under load

Fan-out

Fan-out is one message going to many receivers. The question is where the copying happens. If each receiver does its own reading and its own work, the cost grows with the number of receivers. If one reader does the work once and hands copies to everyone, the cost stays flat.

Thundering herd

A thundering herd is many waiters woken by the same event, all rushing at the same resource. In our feed, when a run's state changes, every open connection for that client calls getRun and threadOfRun at the same instant: ten tabs, ten identical database reads. ticket 11

Head-of-line blocking

In a queue processed in order, a slow item at the front holds up everything behind it. In followFeed, the read loop awaits refreshRun before it handles the next entry. A slow query on one run therefore delays the tokens of every other run on that connection.

Reconnection storms, backoff and jitter

When a backend task restarts, every client connected to it notices at the same moment. If they all retry after 1 s, then 2 s, then 3 s, they arrive in synchronised waves (a reconnection storm), and each wave can knock over the servers that are left.

  • Exponential backoff doubles the wait after each failure (1 s, 2 s, 4 s, 8 s…, up to a cap), so a struggling server gets room quickly.
  • Jitter randomises the wait so clients spread out instead of arriving together. The best-known variant is full jitter: wait a random time between 0 and the exponential ceiling. It comes from an AWS Architecture Blog article, "Exponential Backoff and Jitter".
Try it: 300 tabs lose the server at t = 0Each bar counts the reconnect attempts in that half-second. The server comes back at t = 3 s.
In our code

feed.ts waits 1000 × failures ms (up to 15 s), and follow-run.ts does the same up to 10 s: linear, with no jitter. ticket 06

10Ordering and state

Snapshots vs deltas

A stream can carry deltas ("token 'Hel' added", "step 3 finished"), which the client applies one after another, or snapshots ("here is the whole run as it is now"), which the client puts in place of what it has. Deltas are small but have to arrive complete and in order. Snapshots are larger, but they repair themselves: a missed one is fixed by the next. Our feed sends both: run.event is a delta, and run.updated, thread.updated and comments.updated are snapshots.

Race conditions and last-write-wins

A race condition is when the result depends on which of two concurrent operations finishes first. With snapshots, the client keeps whichever arrives last (last-write-wins). That's only correct if "last to arrive" is also "most recent", which isn't guaranteed when two reads run at once:

sequenceDiagram
  participant F as followFeed
  participant DB as Postgres
  participant S as Studio cache
  Note over F: step event → 800 ms timer
  F->>DB: (timer) getRun — slow
  Note over F: run.completed arrives
  F->>DB: getRun — fast
  DB-->>F: status: completed
  F->>S: run.updated {completed}
  DB-->>F: status: running (old read)
  F->>S: run.updated {running}  ✗ stays wrong

There are two standard fixes:

  • Serialise per key: run one run's reads one after another, so the last one started is the last one sent.
  • Version the snapshots (an updatedAt or the run's last seq): the client ignores a snapshot older than the one it holds. This is also called optimistic concurrency.
Found in review

This race is in feed.ts. The ticket serialises the reads per run. ticket 01

Throttle vs debounce

Both limit how often something runs when events come in bursts:

  • Debounce waits until the burst has been quiet for N ms, then runs once. It suits a search box.
  • Throttle runs at most once every N ms, however long the burst lasts.

Our feed throttles. The first event of a burst starts an 800 ms timer, events during that time are covered by it, and when it fires the run is read once. A run that streams steps continuously is refreshed about once a second, not never (a debounce would never fire) and not on every event.

11In the browser

Push into the query cache

TanStack Query caches server data under keys and re-renders the screens that use a key when its value changes. A live feed can feed it two ways:

setQueryData

"Here is the new value." It is written straight into the cache, with no request. Used for the snapshots: run.updated, thread.updated, comments.updated, setup.updated.

invalidateQueries

"What you have may be stale." Screens that are showing the data refetch it. Used once after each reconnect, since anything may have been missed.

In our code

queries/use-feed-sync.ts, mounted once in studio-layout.tsx. Pushing snapshots, then invalidating everything once after a reconnect, is exactly what TanStack's docs recommend for WebSocket and SSE data.

Batching with requestAnimationFrame

The browser paints about 60 times a second. requestAnimationFrame(cb) runs cb just before the next paint. If 200 tokens arrive within one frame, re-rendering React for each one is 199 wasted renders. Collecting them and applying the batch once per frame keeps the page smooth.

In our code

use-run-stream.ts pushes each event into pending and schedules flush with nextFrame. One thing to know: browsers pause animation frames in hidden tabs, so events pile up while a tab is in the background and are applied in one go when it's shown again. That's fine at our volumes.

Page visibility and online events

Browsers throttle timers in background tabs, and a sleeping laptop has no network. Two events say when things are back:

  • document's visibilitychange (with document.visibilityState === 'visible').
  • window's online.

A good live client listens to both and reconnects at once, instead of waiting out a backoff timer that was set while the network was gone.

Found in review

Once our feed is failed (say, a 401 after the laptop slept), it never tries again, and no screen shows that it stopped. ticket 07

Validating each event

Every frame's JSON is checked with Zod (WireEventSchema.safeParse). safeParse returns success or failure instead of throwing, so one bad frame is skipped instead of breaking the stream. The Studio's "soft parse" goes one step further: on a mismatch it logs and uses the raw value. Parsing every token has a CPU cost; it's small, but it grows with ticket 12's question of how many tokens each tab receives.

Found in review

follow-run-live.ts calls JSON.parse without a guard, so one malformed frame retries the whole history read. ticket 09

12Lifecycle and security

Graceful shutdown

On a deploy, ECS sends the old task SIGTERM ("please stop"), waits stopTimeout (30 s), then sends SIGKILL (stopped at once). A graceful shutdown uses that window to stop taking new requests, let the current ones finish (draining), flush logs and telemetry, and exit cleanly.

Long streams break draining, because they never finish on their own. So a server should end them on purpose at the start of shutdown. The client sees a normal close and reconnects, to a new task. In Fastify the place for that is a preClose hook, which runs before Fastify waits for in-flight requests.

Found in review

Nothing ends our SSE streams on shutdown, so closeApp() probably waits until the 25 s hard exit. ticket 04

Authentication happens once

An HTTP request is authenticated when it starts. An SSE response is one request that lasts for hours. If the person's access is removed, or their token expires, the stream carries on regardless. The common remedy is a maximum connection age: close each stream after, say, 20 minutes, with a little randomness. The client reconnects, which re-checks the token and permissions, and long-lived connections move onto newly started tasks too.

Plan

Close after 20 minutes ± 10 %, writing nothing, so the client reconnects as it would after any clean close. ticket 10

Not leaking internals in errors

Error text from a database or cache can contain host names, key names or SQL. Sending it to a browser tells an attacker about your internals for nothing. The standard practice is a generic code to the client and the full error in the server log.

Found in review

event: stream-error sends error.message to the browser. ticket 08
