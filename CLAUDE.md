# Dugout (FanOS agent harness)

Thin TypeScript agent harness: loop, tools, guardrails, event stream, durability, memory. Agents are a spec plus typed tools on top. Plan and task IDs (H*, M*, S*, E*): `docs/PLAN.md`.

## Layout

- `packages/contracts` — zod contracts (AgentSpec, Tool, RunEvent, Steps, ModelClient). No framework types cross these.
- `packages/core` — loop over `Steps`, tool pipeline, redactor, Bedrock model client (ADR 0012), run log, `runLocal`; stop reasons, model retries and when `final` is accepted (ADR 0018); run hooks, the per-turn rules the harness and an agent plug in (ADR 0023); a run stops for a person (ADR 0029): one pause with typed questions (`Question` in contracts), for the built-in `ask` tool, a tool that throws `AwaitingAnswers`, a child run that waits, or a write waiting for a yes (a `review` question with the call under review). The answers (`{ by, answers? }`) resume the call that asked; a question left out is skipped, no answers at all lets the agent decide, and nothing but cancelling ends a pause for questions. What a person answers to a question the agent declares (`questions` in its spec, by id) is kept in memory (ADR 0033): about one section it is a decision (episodic, keyed by the asking agent, the question id and the section's structural signature, which `frame.load` and `bind.load` set with `ctx.situate` and a child inherits); about the club it is a proposed fact. The next ask is proposed this section's decision, else the house fact, and only an active fact answers it without asking; `frame.load` and `bind.load` return a section's earlier decisions as `before`; `--yes` takes each question's `proposed`
- `packages/db` — Postgres pool, `withTenant` (row-level security), SQL migrations
- `packages/memory` — semantic/episodic store, hybrid search, skills loader, context builder (stable memory in the system prompt, lessons and approved examples in the first user message; ADR 0013), consolidation; decisions and facts from what people answered (`decisions.ts`, ADR 0033): a section answer the same on three sections is proposed as the club's fact
- `packages/mcp` — MCP servers as tool sources (ADR 0026): agents ask for capabilities (`requires`/`optional` in the spec); the registry `config/mcp/<server>.json` says which server has them, each tool's effect and the grants' argument limits; the lock `<server>.lock.json` pins what the model reads (tools, the server's instructions, granted resources, read with `<server>.readResource`) and a call is refused when the live server differs. The model reads a result's text; code reads its `structuredContent`. A grant can limit arguments (`arguments`) or set them for the model (`set`). Connects through the official MCP SDK with per-tenant OAuth (ADR 0022). A grant is read from a file (`pnpm agent mcp login`) or, when the entry's `auth.surface` url and key are set (`SURFACE_API_URL`, `SURFACE_SERVICE_KEY`), from the sign-in a person made in Surface Studio's Setup page: the backend keeps it, the worker refreshes it and hands each rotation back (`surfaceTokenStore`); the tenant id is then the FanXP client code, and the server's URL must be on the same backend that issued the grant. `adapters/cast.ts` is the interim Cast-specific code, structured data only (`.scratch/generic-mcp/cast-asks.md`); `@dugout/mcp/testing` is a fake hub for agent tests. dugout's own Cast hooks have ids that start `dugout_` (names `dugout: `), a rule in the registry
- `packages/library` — the section library (`.scratch/section-library/spec.md`): each Handoff's sections, found from its IR (full-width bands, and containers layout detection names), each with a picture (its plate, cut from one around it, or put together from those inside it), a structural summary from the IR and a vision model's caption and tags, embedded as words and as a picture; searched by words, a picture or both. One row per shape per tenant (the IR's structural signature over the whole subtree), with every Handoff it was seen in. The IR is read by ref and never stored. A section is shared with every tenant once a preview was built from it (unless its tenant stops sharing): the worker does it after each completed frame-match, section-builder or data-bind run (`onCompleted`; `LIBRARY=off` leaves it out), indexing the Handoff first when it is new. Another tenant sees its skeleton, boxes from the IR in its own colours (the house fact `library.palette`, proposed from its own designs, neutral until a person approves it), never its picture or which club it is. A bound preview gives each section its data shape: the fields, types and lists the binding plan reads, never a value, searched with its words. Tables `library_sections`, `library_tenants` in `harness`; pictures in `.runs/library/`
- `packages/evals` — graders, model judge, suite runner and pass-rate gate
- `packages/tracing` — run events → OpenTelemetry spans → Langfuse
- `packages/sdk` — `defineAgent` (what agent packages are written with), live deps, seeding, agent discovery (ADR 0007); subagents: `agents: [...]` makes each a tool, `agent.<camelId>`, that starts a child run under the same tenant and budget; a call to a child that writes is itself a write, approved for each try, builds one thing per run, and a failed try may be repeated up to three times (ADR 0025). A child's events go to its parent's stream (one stream per invocation), tagged `child: { runId, agentId, parentRunId, callId }`; a child's ending ends the child, never the stream (ADR 0031); `@dugout/sdk/testing` is the `drafter` test agent that the worker's, the terminal's and the SDK's tests run against
- `packages/tokens` — token compiler: raw theme export to normalized vocabulary, lint, CSS and types
- `packages/dsl` — the SDUI vocabulary: flat tree format, validator, agent JSON Schema; page choices (`page.ts`, ADR 0032): a node with `select: { key, value }` is one option of a choice the page holds (a tab), and any section's `when` reads it as `_page.<key>` (`eqPath` compares an item's field with it); an `Input` (what is typed) and a `Checkbox` ("true"/"false") write `_page.<key>` the same way, real form controls in the design's look, which `packages/compile/src/fields.ts` finds in a frame's IR (a placeholder in a bordered box, a small box beside text)
- `packages/surface-canvas` — the Figma plugin: Health, Layout, Handoff, and the Frame IR schema
- `packages/compile` — Frame IR to DSL tree
- `packages/conform` — the geometry gate: a compiled tree against its IR
- `packages/renderer` — the rendering SDK (React Server Components) and the Playwright pixel harness
- `agents/frame-match` — matches a compiled Figma frame to its screenshot, from a Handoff stored in the control plane (ADR 0019). Code fixes what needs no judgement, the model adds overrides, and each is measured and undone if it doesn't help. It also says what each container is (ADR 0024): a carousel the frame shows is applied, tabs (a segmented toggle too) become options of a page choice, and what the frame cannot show is asked of a person by `frame.layout`, as questions. It reads whether anything on the section is data (`content.ts`: none, some, unsure; ADR 0032) and records the page choices a published section writes (`page_choices`). It finds the frame's slots (`findSlots` in `packages/library/src/slots.ts`: the parts that each show one kind of data, over a background; a designer's marks come first: a Section note (its text the section's name; layers noted alike are one section) or Background note in the plugin, or a layer named `section/<name>` or `background`, IR 1.13.0). When the finder is unsure which parts are one section, `frame.load` asks once before it builds (`section_split`; the answer is a decision on the frame and is not asked again) and answers with `slots`: each one's tree nodes, `content`, the page keys it writes and reads, and its signature; a choice belongs to the slot that draws it, and with several slots its key is named for the slot (ADR 0032, amendment)
- `agents/section-builder` — the whole job for one Handoff, as one run: a parent whose one tool, `page.build`, runs `frame-match` and then `bind` in code, in that order (a pipeline, ADR 0025), and hands over one preview with its data bound and everything still off from both. A person approves `page.build` once; it covers the children's writes. A frame of several slots (frame-match's `slots`) is bound slot by slot: one `bind` run for each slot with data, keyed by the slot's id and one at a time (`concurrency: 1`: Cast's 25 live runs an hour are shared), their plans put side by side by `src/merge.ts` (a plan that names a node another names is left out), checked over the merged tree and published once with every source in one data map; the output's `slots` says what became of each, and a slot out of tries is reported while the others are published. A frame of one slot runs as before. A section frame-match reads as having no data (a heading, tabs, a button) skips `bind` and is handed over with `data: "none"`. This is what `pnpm agent watch` starts for each Handoff
- `agents/data-bind` — binds a published frame to data: which node shows which field, what repeats, which shape an item draws in, as a binding plan code applies and checks. With no `--data` it calls `hook-maker` (a child run) for the data: one of dugout's Cast hooks, found, or a new one built when none fits (a person approves each try; a failed try may be repeated, three at most, and one that completed is never built twice), and binds that hook's live output. A section's static parts (a heading, a button, a note) stay as designed and are named in the plan's `keep`, with why: `bind.try` accepts what is reported on them and says `publishable`, so `bind.publish` is called once; `despite` publishes what can be neither fixed nor kept. `bind.static` ends a run on a frame with nothing on it that is data (a newsletter sign-up too); given a `slot` (frame-match's `slots`) it binds that slot's nodes only, follows the choices the slot draws, and ends with `bind.done` (the pass publishes once); `bind.source` may be called once for each data source (`as` names it, and the plan reads them all from one bag), and the published `data` meta lists every source; `bind.load` lists the page choices other sections write, and `links` names a list whose items hold one's values, for a `when` with `eqPath`
- `agents/ui-editor` — changes a published preview as the comments a person left on its elements ask: `ui.load` reads the open comments (`ui_comments` in the harness database, read with the harness's pool for the run's tenant; Surface Studio's backend writes them, `POST /surface/runs/:id/comments`) with each element's props; `ui.try` applies prop edits in memory and checks them against what each primitive takes (`propIssues` in `@fanos/dsl`); `ui.publish` (a write, approved) stores the changed tree as a new `dsl_tree`, marks the comments `sent` and answers the preview link. Input is the preview link; run it with `pnpm agent ui-editor --tenant <t> --preview <link>` (Surface Studio's Comments tab copies the command). It edits props only: a comment that asks for a new element or new data is reported not-addressed. The editor itself (Edit on the queue canvas: select an element, an Advanced panel of that primitive's properties, a comment box) is in `wnm-fanxp-frontend` `apps/surface-studio`; its per-primitive panels are generated here from the DSL's field descriptors (`pnpm tsx scripts/panels.ts <out.json>`, written to `features/queue/lib/panels.generated.json` there), and its comments go to `wnm-fanxp-backend` `/surface/runs/:id/comments`
- `agents/hook-maker` — gets a design's data out of Cast (ADR 0030): finds the `dugout_…` hook that gives it, runs it live and says what it covers and lacks; builds a new one from the tenant's API connectors only when none fits (create, call, run, transform, run with it, publish), asking the person first when a hook gave part of it. Capability `hooks.author` (writes only `dugout_` hooks, reads any); `bind` calls it as `agent.hookMaker`, which a person approves for each try
- `apps/worker` — runs agents (ADR 0009): claims queued, decided and orphaned runs from Postgres, holds a lease per run, saves its working memory (ADR 0006), writes events to the Valkey stream + Postgres record, hands runs over on SIGTERM; no port; `Dockerfile` for ECS. Also the queue a host uses to hand it runs. A queued run that names a parent (`parent_run_id`) and has no save point of its own is a follow-up: the worker forks the parent's latest save point and the run's input is the corrected input (`queue.continueFrom`; ADR 0016), which is how a thread of runs, such as `ui-editor`'s, keeps its context. Every run is in a thread (`threads`, ADR 0031): a Handoff starts one and every later run about that section joins it (the `runs_thread` trigger: a child, follow-up or fork is in its parent's, a run on a preview in the thread of the run that published it); `queue.start(..., { threadId })` (and `pnpm agent <id> --thread <id>`) names one; a thread is never guessed from a run's input. Each run a host started leaves a note in its thread (`thread_notes`: what it did, made, a person decided, left open; the agent's `threadNote` says what it did), and the next run in the thread starts with them under `## This thread so far`, within 1,500 tokens; child runs read and write none (`packages/memory/src/thread.ts`) Temporal replaces the claiming before production (H7)
- `apps/cli` — the terminal host for the worker, doing what wnm-fanxp-backend will: queues a run, follows its events, asks at each approval and queues the decision
- `apps/api` — the control plane (:4100): artifact store, Handoffs, surface versions, pipeline runs, fidelity gate; its own database (`fanos`, ADR 0021) and job worker. Retiring: the end state is two databases, FanXP's and `harness` (ADR 0027), and agents still read their input from it until a Surface MCP server exists. The whole flow and its components are in `docs/architecture/handoff-flow.md`

## Commands

- `pnpm check` — lint + typecheck + test (what CI runs)
- `pnpm format` — Biome autofix
- `pnpm infra up|down|reset` — Postgres+pgvector (:55432) and Valkey (:56379). Tests need these up. `pnpm infra up pipeline` adds the pipeline's Electric. `reset` deletes dugout's volumes
- `pnpm db migrate [harness|fanos|all]` / `pnpm db seed` — apply migrations (harness by default; `fanos` is the pipeline's); load each tenant's house facts (`config/tenants/<tenant>/facts.json`) into memory. Every agent of a tenant reads all of its memory (ADR 0013)
- `pnpm worker` — runs the agents; `pnpm agent` needs one running. `AGENTS=frame-match` limits it to some agents
- `pnpm agent` — menu of commands when a terminal is attached; `pnpm agent --help` lists them. `pnpm agent <id> --tenant <tenant> --<input field> <value> [--input json] [--model <name>] [--effort <level>] [--yes]` queues a run and follows it (flags left off are asked; `--yes` approves each approval without asking, recorded as made by you, auto). `--model` is a name in `config/models.json` (it applies to the run and every child run below it) and `--effort` is low, medium, high, xhigh or max, as far as the model takes it: `sonnet@high` is also a model name. A terminal asks for both in the menu. At an approval, a terminal offers Approve, Reject, or Request a change; a pipe answers `y`, `n`, or the change. Ctrl-C leaves the run going; `pnpm agent attach --run <runId> --tenant <tenant>` (or `--run`) attaches again; `pnpm agent cancel <runId> --tenant <tenant> [--reason <why>]` (or `--cancel`) stops it. `pnpm agent runs --tenant <tenant>` lists recent runs; `pnpm agent history [run] --tenant <tenant>` (or `--history`) lists a run's save points; `pnpm agent fork [run] --from <version> --tenant <tenant>` (or `--fork`) starts a new run from one. `pnpm agent agents` lists agents
- `pnpm build` — build every `@fanos/*` package and app (the agents load their `dist`). `pnpm infra up pipeline` — Electric (:3010) and the `fanos` database; `pnpm db migrate fanos`; `pnpm dev` — the API and its worker
- Databases run in Docker, apps on the host (ADR 0021). `pnpm infra up` is one Postgres (:55432, databases `harness` for dugout and `fanos` for the pipeline) and one Valkey (:56379; the pipeline's job queue is its database 1). `pnpm infra up pipeline` adds Electric (:3010) and creates `fanos` on an existing server. `pnpm db import` copies the old trial stack's database into `fanos`
- `pnpm agent memory review --tenant <id>` — approve or reject proposed facts (edit one proposed from people's answers first: its sentence and its answer); `--shared` for proposed shared memory
- `pnpm agent memory decisions --tenant <id> [--section <signature>] [--list]` — what people decided about sections when a run asked; forget one
- `pnpm agent memory fact --tenant <id> --key <key> [--value <answer>] [--approve] "<fact>"` — a house fact a person writes (proposed, or active with `--approve`). `media.<what>` facts give a picture URL the data has no field for, built from an item field (`--key media.player-photo "Player photos: https://…/players/{id}.png"`); data-bind binds a picture's src with it, and its picture check reports a collapse that would draw the first card's photo on every card
- `pnpm agent memory promote` — propose facts and lessons that several tenants hold as shared memory, for their sport or for every tenant (ADR 0014)
- `pnpm eval frame-match [--model <name>] [--only id,id]` — eval suite; exits non-zero below the 90% gate. `--model` runs the agent on another model in `config/models.json`
- `pnpm agent data-bind --tenant demo-cricket --preview <frame-match preview link> [--data <dataset>]` — bind a frame to data; without `--data` the data is found in Cast, or a hook is built there (needs `CAST_MCP_URL` and a `cast:login` grant). `pnpm agent hook-maker --tenant demo-cricket --input '{"need":{"list":"fixtures","count":"data","item":[{"field":"score","required":true}]}}'` runs the find-or-build alone (need is structured: list, count, groupBy, item, must, hints, hook). A child run is in `pnpm agent runs`, and `pnpm agent attach --run <id>` follows it
- `pnpm eval measure [--write [--all]]` — the code-only result for each eval frame and each held-out design (no model), next to `agents/frame-match/evals/baseline.json`; `pnpm eval vision` — breaks frames in known ways and measures whether `frame.look` finds them, against the score; `FRAME_MATCH_VISION=off pnpm eval frame-match` — the same eval with `frame.look` answering "not available"
- `pnpm agent watch --tenant demo-cricket [--project default] [--latest] [--model <name>] [--effort <level>] [--ask]` — press Handoff in the Figma plugin and a `section-builder` run starts (one run: the frame is matched and published, its data is found in Cast or a hook is built there, and it is bound), followed here with one preview with data printed at the end; it publishes without asking (`--ask` brings the prompt back, once for the whole pass). `pnpm agent section-builder --tenant <t> --export <id>` runs one export the same way; `frame-match` and `bind` still run alone. Needs `pnpm worker` and the control plane (:4100). `pnpm agent frame-match --tenant <t> --export <id>` runs one export
- `pnpm agent mcp list` — the registry's MCP servers, whether each is configured here, its lock, and what each capability grants. `pnpm agent mcp sync <server> --tenant <t> [--check]` — writes the server's lock from the live server (review its diff: it is what agents read); `--check` exits 1 when it is stale. `pnpm agent mcp login <server> --tenant <t> --site <code>` (or `pnpm --filter @dugout/mcp cast:login --tenant <t> --site <code>`) — one browser login per tenant for an OAuth server; Cast needs `CAST_MCP_URL` in `.env`, and keeps grants in `CAST_MCP_TOKENS` (default `.runs/cast-mcp.json`). `frame-match` gets Cast's read tools only when Cast is configured. Run one worker per token file
- `pnpm eval layout` — what each container of the eval frames is (carousel, list, row, grid, tabs), from the IR alone, against `agents/frame-match/evals/layouts.ts`; exits non-zero on any miss (ADR 0024)
- `pnpm eval sections` — the section finder on each case of `agents/frame-match/evals/sections.ts` (the Team frame with and without marks, Fixtures, LATEST NEWS, Videos; IR copied in `evals/sections/`): background, bands and slots against what a person reads in the design (`.scratch/page-sections/`); code only, exits non-zero on any miss
- `pnpm eval smoke [--model <name>]` — one minimal live run, on `nova-lite` unless named
- `pnpm agent library index --tenant <t> (--handoff <id> | --latest <n> | --all) [--no-caption] [--model haiku]` — adds Handoffs' sections from the control plane (`pnpm dev`) to the tenant's section library; `pnpm agent library search --tenant <t> "<words>" [--shared] [--image <png>] [--kind <k>] [--layout <l>]` searches it (`--shared`: other tenants' previewed sections too, as skeletons); `pnpm agent library previews --tenant <t>` shares the sections of every Handoff the tenant's runs previewed; `pnpm agent library share --tenant <t> [--on|--off]`; `pnpm agent library palette --tenant <t> [--propose]` the colours another club's skeletons are drawn in for it, from its own designs
- `pnpm agent schemas` — write each agent's input and output JSON Schema to `schemas/` for hosts; a test fails when they are out of date

## Rules

- Two families share `apps/` and `packages/`, told apart by npm scope. `@dugout/*` is the harness. `@fanos/*` is the Figma-to-SDUI pipeline (formerly the `trial` repo, ADR 0020): it has its own toolchain (tsup, vitest 2, TypeScript 5, `tsconfig.fanos.json`), builds to `dist`, and is not yet linted by Biome (the exclusions are in `biome.json`). The agents load its built `dist`, so run `pnpm build` after install and after changing it.
- Internal packages export `src/index.ts` directly; no build step. Run TS with `tsx`.
- Tenant id comes from verified run context, never from the model or tool input.
- Typed tools only — no generic shell. Write-effect tools go behind approval.
- A tool that cannot go on until a person sets something up (a sign-in, a key) throws `NeedsSetup`: the run ends `needs setup: …` at once, and a parent does not retry the child (ADR 0032).
- An MCP server's tools reach an agent only through its registry entry (`config/mcp/<server>.json`: each tool's effect, and the capabilities that grant it) and its lock. After a server changes, run `pnpm agent mcp sync` and review the lock's diff before committing it. Server-specific code goes in `packages/mcp/src/adapters/`, never in an agent.
- An agent is `agents/<id>/`: `src/agent.ts` calls `defineAgent`, `src/index.ts` exports `agent`, plus `skills/` and `evals/suite.ts`. Add it to the worker's list in `apps/worker/scripts/work.ts` for the worker to run it.
- A skill in `skills/` is in the spec's `skills` (always in the instructions) or `onDemandSkills` (listed by its frontmatter `description`, loaded with `skill.load`; ADR 0011).
- Nothing in an agent folder is per tenant (ADR 0010). What differs by tenant is house facts in memory, or data a tool reads with the verified tenant id. Demo tenants keep theirs in `config/tenants/<tenant>/`.
- Only the consolidation workflow writes long-term memory; agents propose.
- Config is read live through a tool, never copied into memory.
- Public npm registry is pinned in `.npmrc` (the global CodeArtifact token expires).
