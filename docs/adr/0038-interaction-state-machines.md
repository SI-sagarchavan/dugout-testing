# 0038 — Interaction: a machine per section, a page of them, on XState v5

Date: 2026-11-11 · Status: accepted · Extends ADR 0032 (its rules kept; `_page` is now one name for the page's values) · From `.scratch/ui-workflows/spec.md`

## Context

A Handoff publishes a section as it looks. Most sections also behave: the header's user menu opens on the arrow and closes on a press outside or Escape, the header is drawn signed in or signed out, SELECT PLAYER opens a drawer whose picks show back on the page, SAVE posts, a cart counts and totals. ADR 0032 gave the DSL page choices (`select`, `_page`) and fields, which cover tabs and filters and nothing that remembers a list, makes a request, or opens and closes.

## Decision

- **A section has one machine, on its tree's root (`props.machine`).** It is JSON, shaped like an XState v5 config (`packages/dsl/src/machine/schema.ts`): `context`, `computed`, `exports`, `states` (the root is parallel by default: a menu, a drawer, a request are regions), `on`, `entry`/`exit`, `always`, `after`, `onDone`, `tags`, and `requests`/`invoke` for what the host runs. It travels with the tree.
- **Guards and actions are data, never code.** A guard, an `assign`, a computed value, an export or a payload is an expression in a closed JSON language (`expr.ts`, JsonLogic-shaped: `var`, comparisons, arithmetic, `map`/`filter`/`sum`/`toggle`/`updateWhere`…, each with a step budget and no way out of plain data). Actions are a closed set: `assign`, `raise`, `send` (to the page), `emit` (tracking, by meaning), `navigate`, `call` (a host action), `focus`, `scrollTo`, `if`.
- **XState v5 runs it, through its pure transitions** (`initialTransition`, `transition`; `interpret.ts`). Our spec is compiled into an XState machine with one guard (`expr`) and one action (`effect`) that XState hands back; nothing in the DSL waits or fetches. Requests, delays, tracking, navigation and persistence are effects the runtime carries out, and answers come back as events (`done.invoke.<state>`, the delay's event). We chose XState over our own interpreter for its tested statechart semantics and its tools; it is 12.9 KB gzipped for what we use. One consequence of its SCXML semantics: a target in another parallel region re-enters the regions between (the validator warns; send an event instead).
- **A page of machines** (`system.ts`): one per section drawn (an instance; the same section twice is two), plus any a host adds with no section of its own (a cart in the layout). A machine is its section's alone. Sections meet in two ways: a machine's `exports` are the page's, by key (`$page.<key>`, one owner each), and `send` offers an event to every other machine that handles it. A change in what the page shares offers each machine `page.changed` and runs its `always`. The host gives `$user` (the signed-in fan, or null) and `$route`; they are read, never written.
- **What nodes read and say.** `$state.active|tags|value|context|computed` (the section's own), `$page.<key>` (also `_page.<key>`: tabs and fields write the same values), `$user`, `$route`, and `$entry` inside a followed list. Conditions gain `has` / `hasPath` (a list holds a value). A node sends events with `on: { click|input|change|submit|outside|escape: { send, payload?, to? } }`; its look follows state with `statesWhen: { active|inactive|disabled|expanded }`; a Repeater with `follow: { list, key, by? }` draws only the data's items that a list in state holds. A Repeater never draws state itself: server data is never copied into a machine (the machine holds ids, a draft, quantities).
- **Server first, then the browser.** The server builds the page system (a host that draws several sections passes one `system` to every `Render`), draws every node as the first moment reads, and writes what each node sends (`data-fos-on`) and which looks depend on state (`data-fos-looks`). Each section's `MachineHost` joins the client store at the server's snapshot, so the first client render is the markup, then starts the requests and delays that snapshot waits on and reads a persisted machine back. Every node stays a Server Component; only gates (`StateGate`), text (`StateText`) and followed items (`FollowItem`) are client components.
- **The host owns the outside world** (`configureRuntime`): requests go to its action route (default `POST /api/actions/<action>`, which resolves the tenant and the fan's session; the page never holds a URL or a credential), tracking to the tenant's sinks (default GTM's `dataLayer`), navigation and storage.
- **S18** checks a tree: the machine is one and is on the root, every event a node sends its section is handled (or goes `to: "page"`), `$state` is read only with a machine and only what it has, a Repeater's `over` is data. `systemIssues` checks a page: a key two sections share, an event nobody handles, a `$page` key nobody shares.

## Consequences

- The header's user menu, signed-in and signed-out drawing, the fan-preferences drawer and its SAVE, and a cart with caps, totals and persistence are trees, not code (`packages/dsl/tests/machine.test.ts`, `packages/renderer/tests/interaction.test.ts`).
- The `@fanos/dsl` package depends on `xstate`; SCRE, which copies the DSL, takes it too.
- Not built yet: the agent side (an `interaction` step that proposes a machine from Figma prototype reactions, variants, notes and comments; asks what the design does not say), the plugin exporting reactions and variant properties, `action-maker` for write endpoints, the host's action route and tracking config, Radix-based `Menu`/`Dialog` primitives (focus trap, anchoring), server data the machine refreshes (`sources`), a Repeater ordered by the state's list rather than the data's, and a Studio panel that shows the machine and lets a person step through it.

## Amendment (2026-11-12): the agent side, first part

- `agents/interaction` makes a published section behave. Code reads the evidence (`ix.load`): the parts of a list's cards whose look differs card to card, lined up by position so a variant card counts; the page's fields; boxes the IR clips whose content runs past them. The model settles what each means and asks only what the design cannot say. It hands `ix.apply` typed behaviours (`toggles`, `show`, `restyle`, `search`, `scroll`), and code writes the machine, the `when`s, each press's event (in the plan, since SCRE draws a tree with refs of its own without its plan) and the list's filter. It then simulates every state of an item with the DSL's own `when` before it publishes.
- The DSL gained what this needed: `containsPath` and `within` (a search), `lacks` and `lacksPath` (an item not in a list), `scroll` on a Stack, and the `lines` pipe.
- section-builder runs it last on every section, and its model says when there is nothing to do (amended 2026-11-12: code no longer decides from the evidence whether it runs); ui-editor hands it comments about behaviour. SCRE carries the machine runtime (`pnpm scre:sync`).
- Still not built: prototype reactions and variant properties from the plugin, `action-maker` and the host's action route (SAVE), Radix `Menu`/`Dialog`, and a Studio panel for the machine.

## Amendment (2026-11-12): more of a data source, and the model writes the machine

- **Code for what a page can reach, config for what it does.** A new kind of interaction is a machine and props the agent writes, never new code; code is added only when a page cannot reach something yet. LOAD MORE needed one such reach: a machine could call a host action but not fetch more of its own data.
- **A request may name a data source** the section reads (`requests: { next_page: { source: "photos" } }`, one of `action` or `source`). The runtime hands it to the host (`configureRuntime({ load(source, input, instance, signal) })`), which runs that source again with the request's input over the inputs it was bound with, adds the answer to the data it holds (`addToSource`: lists appended, objects key by key, the rest replaced: the same in every host) and draws the section again; the machine gets `done.invoke.<state>` or `error.invoke.<state>`. The machine still never holds server data: it holds which page it asked for. S18 refuses a source no node of the section reads. Hosts: Surface Studio's canvas (through `GET /surface/runs/:id/section/live?source=&input=` in wnm-fanxp-backend, which runs only that source); the default runtime rejects.
- **A Repeater's `slice: [start]`** draws from `start` to the end of the list, however long it grows: the cards after a mosaic bound by position, where the pages LOAD MORE adds are drawn.
- **LOAD MORE is config**: the hook takes a `page` input and answers `next` (hook-maker's `need.paged`); data-bind binds the cards after the design's own looks as a list with an open slice; the interaction agent's model writes the machine (a state that makes the request, a page counter) and, on the button, `on: { click: { send } }` and `when: { path: "<source>.next", exists: true }`, so it is gone on the last page.
- **The interaction agent writes machines itself.** `ix.apply` takes `machine` (the section's, whole) and `props` (`on`, `when`, `statesWhen`, `follow` on layers) besides the typed behaviours, which remain the short way for picks, looks, search and scroll. Its skill `machine` is the language with LOAD MORE as the worked example. The check runs S18 and the machine itself, event by event (`states`: what each press does, what it asks for, what is drawn after).
