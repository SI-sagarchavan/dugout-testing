# 0025 — Subagents are tools that start a child run

Date: 2026-11-04 · Status: accepted (the `pipeline` option was replaced by `defineWorkflow`, ADR 0037, on 2026-11-11; child runs, their approvals and their tries are as written here) · Extends ADR 0017 and ADR 0023 · Resolves harness-orchestration ticket 07

## Context

Only code (a program, ADR 0017) could run several agents. Binding a frame to its data needs an open-ended search first: which of a tenant's Cast hooks gives what the design shows. That means listing hooks, reading their definitions (a few thousand tokens each) and running one. Done inside `bind` it fills `bind`'s context with hook prose it never needs again. The search is a separate job with a short answer, so it belongs in its own run with its own context.

## Decision

- **A spec lists the agents it may call** (`defineAgent({ agents: [hookFinder] })`, so `spec.agents: ["hook-finder"]`). Each is a tool, `agent.<camelId>` (`agent.hookFinder`), whose input is that agent's input schema and whose description is the child's `spec.description`. The model never names an agent that isn't listed. `budget.maxDepth` must be 1 or more for a spec that lists agents.
- **A call starts a child run**, in the parent's tool step, in the same process:
  - its own transcript, checkpoint, save points and events, under the parent's tenant;
  - the child gets only its typed input, never the parent's transcript;
  - its run id is derived from the parent run id and the call id (a version-5 UUID layout), so a parent resumed mid-call starts the same child, which carries on from its save;
  - the tool result is `{ runId, output }`; a child that fails is a tool error naming its run.
- **A run that ended keeps its ending.** The checkpoint has an optional `ended` (`completed`, `rejected` or `failed`, with the output or reason). A run resumed after it ended returns that and does nothing else: no events, no model call, no `afterRun`. This is how a resumed parent gets its child's answer. A fork drops `ended`.
- **Budget is shared.** The loop passes each tool step what the run has left (`usdLeft`). The child runs with the smaller of its own `usdPerRun` and that. A tool reports what it spent besides the run's own turns through `ctx.spend(usage)`. The loop adds it to the run's usage (tokens and dollars, not steps), puts it on `tool.completed` as `usage`, and ends the run with `budget` as soon as a call takes it over.
- **Depth.** A run's context has `depth` (0 for a run a host started). A child runs one level below its caller, and is refused when that would be deeper than the calling agent's `maxDepth`.
- **A child that writes is approved as one call** (amended 2026-11-04, for `hook-maker`). The parent's tool to it is a write, so the parent's call waits for a person like any write, in the worker too. That yes covers the child's own writes: its approver grants each, `by` "the call that started this run (<parent run> <call>)", so the record says whose yes it was. What the child may write is bounded by its own tools, in code (hook-maker writes only the one `dugout_` hook it creates). A child that only reads is called without approval, and its approver refuses any write that reaches it.
- **A child that writes builds one thing per parent run, and may be tried again when a try fails** (amended 2026-11-04). A try that completed is final: its answer is kept, and a later call to the child is refused before anyone is asked, with that answer, so nothing is built twice. Found live: `bind` called the builder a second time with a better input, and two hooks were built. A try that failed is not kept: the next call starts a new child (its run id is the agent's id and which try it is, the first keeping the id it always had), after a person approves that call too. The approval shows which try it is and what the last one failed on (the call's input gets a `retry` note, which the child never sees). After `MAX_WRITING_ATTEMPTS` (3) failed tries the call is refused and the run says a person has to look, so unattended approval cannot loop. Which tries ended is read from the run store, so a restarted worker counts them right. A child that reads runs per call.
- **The builder checks for what exists first.** It lists its hooks and finishes one that already fits, or a draft an earlier try left, instead of creating another; its finish check needs the hook run with its transform and published after the last change this run made to it, not a create (a create never overwrites, so a retry that wants a fresh hook takes a new id).
- **A pipeline runs agents in a fixed order, in code** (2026-11-04, for `section-builder`). When the steps are known, the model does not decide them (the harness spec's R5: prefer a program when the steps are known). `defineAgent({ agents, pipeline })` gives the parent one tool, `pipeline.name`, instead of an `agent.<id>` per child: the model cannot call a stage alone or out of order. The pipeline's `run(call, input)` is plain code: `call(child, input)` runs one child and answers with its output. The tool is one write a person approves once, and every child's writes go through under that yes; so a pass is one run with one approval, one cost and one result. Each child keeps its own tries (a stage that completed stays done when the tool is called again after a later stage failed; a failed one may be tried again, each call approved, up to `MAX_WRITING_ATTEMPTS`), and a repeat call's approval names the stage and what it failed on. Cost: a child's approvals ride under the one yes, so a question that a child puts to a person through an approval (frame-match's `frame.layout`) is answered by the proposal, and frame-match says so in its `remaining`; asking the person for those too would mean approvals passing up through child runs, which is not built.
- **The agent tool is `resumable`.** A crash mid-call is safe to run again even when the child writes: the child carries on from its save. A write tool without `resumable` (or `retries`) is still reported as an unknown outcome and not run again.
- **A child runs on its own spec's model, unless the host named one.** `--model` (the run's `model`) applies to the whole tree: the run it started and every child below it (amended 2026-11-04: it was for the started run only, and a run meant to be on one model was half on another). Without it, each runs on its spec's model.
- **In the worker** a child has a `runs` row of its own (`apps/worker/src/children.ts`): `parent_run_id`, and `parent_call_id` (migration 012), held by the parent's lease, saving through the parent's run store and writing to the same sinks under its own run id. `claim_runs` skips rows with a `parent_call_id`: a child is never claimed on its own, only started again by its resumed parent. A fork names its parent too, with `parent_version`, and is queued like any other run.
- **A pipeline may call one writing child several times, each under a key** (2026-11-09, for a frame of several slots, `.scratch/page-sections/`). `call(child, input, { key })` names the call. Each key is a child of its own: the run id comes from the parent run, the agent and the key (`attemptId`; no key is the id it always had), a completed key is answered again without a new run, and each key has its own three tries (`block`, the repeat call's approval and the failure a person is shown all name the key). Calls with different keys may be started together (`Promise.all`); the pipeline's `concurrency` (default 2) is how many run at a time. A pipeline call does not end while one of its calls is still running: a pause or a failure waits for the rest to settle, so no child runs on while its parent waits, and a resumed parent never starts a second run of the same child. A child's events carry its key in the `child` tag (`ChildRef.key`), which the terminal shows (`▸ data-bind (squad)`).
- **When two keys ask, the pauses are one at a time** (ADR 0029). The pause carries the questions of the first child to ask. The answers come down with the resumed call naming the runs they came from (`answered.from`), and only that child takes them; the other, still waiting, asks again and is a pause of its own. Merging the questions into one pause would need their ids made apart (two children both ask `kind`), and what a person answered is a decision keyed by that id (ADR 0033).
- **One thing built per input, not per parent run** (2026-11-09, found in run `8758c3d4`: a person's answer put the Southern Brave feeds in the second `agent.hookMaker` call, and it was answered at once with the first try's output, unchanged, so the feeds were never read). A completed try answers only a call with the same input (`inputKey`: the canonical JSON of the input, keys sorted, without `retry`). A call with a different input is a new try: the next number, its own run id, approved like any try, and it counts toward `MAX_WRITING_ATTEMPTS` only if it fails. A try that completed and built nothing (`hookId: null`) is no reason to refuse a new input. When the input is the same, the answer says so in words ("already asked this same need in this run and answered it … change the need to ask again"), so the model does not report it as a fresh result. The child's checkpoint keeps the hash (`inputHash`), so a restarted parent finds the try for each input in the run store. Reviewed the same day: a try that never ended (it waits for a person, or a crash or timeout cut it short) is taken up again only for its own input; any other input is a new try, so one input's output is never saved under another's. The child's checkpoint also keeps the parent's call that started it (`parentCallId`): a restarted parent reads its children's tries from the store before its first turn (`ChildCaller.load`), so a later call asking the same again is refused with the earlier answer ("already answered for this same need") before anyone is asked to approve it, and code calling it gets that answer with `again: true`; the call a crash cut short is its own try, taken up again, and reads as a fresh answer. A completed try saved without a hash matches no input. Every try counts toward `MAX_WRITING_TRIES` (5 per parent run and key, completed or failed), besides the three failures: past it the call is refused, saying a person has to look, so a model that keeps changing the need still ends.

## Consequences

- `bind` hands "find the data" to `hook-finder`. bind's context gets about a dozen lines (the hook, its input, covers, missing) instead of the hook definitions. The researcher's run is in `pnpm agent runs` and can be attached to by its id.
- One model call can start a whole run. The shared budget and `maxDepth` cap that. The child's events go to its own stream: a host following the parent sees `agent.hookFinder` start and complete, with the child's run id and spend.
- The tool's timeout (15 minutes) doesn't stop a child that is still running. The child is bounded by its own steps and budget.
- `run.started` carries `parent: { runId, callId }` on a child, so traces and hosts can link the two.
- A person approving a writing child approves its whole job at once, without seeing each write. That is the point (a build is a dozen writes), and it is safe only while the child's tools confine what it writes. A child whose writes need a person each would make the parent wait on the child's approval: not built.
